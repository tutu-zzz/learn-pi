## 2026-10-08

### V0.2 — Conversation

**状态：测试通过**

`micro-pi` 已支持同一次程序运行中的多轮对话，能够通过重复发送消息历史记住前文，实现**会话内的短期记忆**。

```text
创建消息历史
  → 读取用户输入
  → 追加 user 消息
  → 发送完整 messages
  → 提取模型回答
  → 追加 assistant 消息
  → 进入下一轮
```

| 阶段 | 代码范围 | 作用 |
|---|---:|---|
| 创建消息历史 | 39–45 行 | 在循环外创建 `messages`，保存整个会话的消息 |
| 多轮对话循环 | 48–57 行 | 持续接收用户输入，并通过 `/exit` 结束会话 |
| 记录用户消息 | 59–65 行 | 将本轮 `user` 消息追加到历史 |
| 发送完整上下文 | 67–82 行 | 将完整 `messages` 放入请求体并调用模型 |
| 记录模型回答 | 85–98 行 | 提取回答，追加 `assistant` 消息并输出 |

验收结果：

- 第一轮告诉模型“我叫小明”。
- 第二轮询问名字时，模型正确回答“小明”。
- 输入 `/exit` 后程序正常结束。
- 当前记忆只存在于程序运行期间，尚未实现跨进程 Session。

#### 记忆能力边界

| 能力 | V0.2 是否具备 |
|---|---|
| 同一次运行中记住前文 | 有 |
| 关闭程序后继续记住 | 没有 |
| `/resume` 恢复旧对话 | 没有 |
| 从大量历史中选择相关记忆 | 没有 |
| 自动提取姓名、偏好等长期信息 | 没有 |
| 历史过长后自动压缩 | 没有 |

因此有两种说法都成立：

- 从用户体验看：**V0.2 有短期记忆。**
- 从实现机制看：**V0.2 只有消息历史，还没有独立的 Memory 系统。**

等以后把 `messages` 保存为文件或数据库，并能重新加载，就是 **Session 持久化**；如果还能提取重要事实、跨会话保存并按需检索，才更接近专门的 **Memory 系统**。

### V0.3 — Tool Calling

**状态：测试通过**

`micro-pi` 已完成一次完整的工具调用：模型提出 `read_file` 请求，Python Runtime 读取文件，再由模型根据 Tool Result 生成最终回答。

```text
定义 Tool Schema
  → 第一次调用模型
  → 解析 Tool Call
  → Python 执行 read_file
  → 追加 Tool Result
  → 第二次调用模型
  → 输出 Final Answer
```

| 阶段 | 代码范围 | 作用 |
|---|---:|---|
| 定义工具 | 44–73 行 | 描述 `read_file` 的名称、用途和参数 |
| 实现工具 | 75–79 行 | 由 Python Runtime 真正读取 `README.md` |
| 封装模型调用 | 81–106 行 | 构造请求并返回完整 assistant message |
| 获取 Tool Call | 128–159 行 | 第一次调用模型并解析工具名与参数 |
| 返回 Tool Result | 161–178 行 | 执行工具并通过 `tool_call_id` 写回结果 |
| 生成最终回答 | 181–186 行 | 第二次调用模型并保存 Final Answer |

验收结果：

- 模型正确生成 `read_file({"path": "README.md"})` Tool Call。
- 文件由 Python Runtime 读取，不是由模型直接读取。
- Tool Result 正确加入消息历史并与原 Tool Call 关联。
- 第二次模型调用能够根据真实文件内容生成最终回答。
- 最终回答已保存到 `messages`，多轮对话历史保持完整。
- V0.3 暂时只支持一个工具和一次工具调用。

## 2026-10-09

### V0.4 — Agent Loop

**状态：测试通过**

`micro-pi` 已将固定次数的模型调用改为 Agent Loop，能够持续完成“模型决策 → 工具执行 → 结果回传”，直到模型给出最终回答。

```text
读取用户输入
  → 调用模型
  → 检查 Tool Call
  → 执行工具
  → 追加 Tool Result
  → 继续调用模型
  → 输出 Final Answer
```

| 阶段 | 代码范围 | 作用 |
|---|---:|---|
| 用户对话循环 | 109–127 行 | 持续接收用户输入，并通过 `/exit` 结束会话 |
| Agent Loop | 130–166 行 | 持续运行模型与工具，直到模型不再发出 Tool Call |
| 模型决策 | 133–137 行 | 调用模型、保存 assistant message，并检查 Tool Call |
| 结束判断 | 139–142 行 | 没有 Tool Call 时输出 Final Answer，结束本轮 Agent Loop |
| 工具执行与回传 | 144–166 行 | 执行本轮 Tool Call，并将 Tool Result 追加到消息历史 |

验收结果：

- Agent Loop 测试通过。
- 模型调用次数不再固定，由任务过程决定。
- 有 Tool Call 时执行工具并继续循环。
- 没有 Tool Call 时输出最终回答并结束本轮循环。

### V0.5 — Tool Registry

**状态：测试通过**

`micro-pi` 已使用 Tool Registry 集中管理工具说明和执行函数，Agent Runtime 能够根据模型返回的工具名称查找并执行对应工具。

```text
定义工具函数
  → 注册到 Tool Registry
  → 生成 Tool Schema
  → 模型发出 Tool Call
  → 按名称查找工具
  → 执行 execute
  → 返回 Tool Result
```

| 阶段 | 代码范围 | 作用 |
|---|---:|---|
| 定义工具函数 | 45–49 行 | 实现 Python Runtime 真正执行的 `read_file` |
| 注册工具 | 52–78 行 | 集中保存工具说明、参数和 `execute` 函数 |
| 生成 Tool Schema | 81–102 行 | 从 Registry 生成发送给模型的 `tools` 列表 |
| 查找并执行工具 | 173–181 行 | 根据工具名称查找 Registry，并使用模型参数执行函数 |
| 返回 Tool Result | 185–192 行 | 将执行结果与对应 Tool Call 关联并加入消息历史 |

验收结果：

- Tool Registry 测试通过。
- 模型使用的 Tool Schema 能够从 Registry 自动生成。
- Runtime 能够根据工具名称找到对应的执行函数。
- Agent Loop 能够使用 Registry 完成工具调用并生成最终回答。
