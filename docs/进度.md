**状态：测试通过**

`micro-pi` 已支持同一次程序运行中的多轮对话，能够通过重复发送消息历史记住前文，实现**会话内的短期记忆**。

```text

  → 提取模型回答

```

| 阶段 | 代码范围 | 作用 |
|---|---:|---|

| 记录用户消息 | 59–65 行 | 将本轮 `user` 消息追加到历史 |
| 发送完整上下文 | 67–82 行 | 将完整 `messages` 放入请求体并调用模型 |
| 记录模型回答 | 85–98 行 | 提取回答，追加 `assistant` 消息并输出 |

验收结果：

- 第一轮告诉模型“我叫小明”。
- 第二轮询问名字时，模型正确回答“小明”。
- 输入 `/exit` 后程序正常结束。
- 当前记忆只存在于程序运行期间，尚未实现跨进程 Session。

#### 记忆能力边界

| 能力 | V0.2 是否具备 |
|---|---|
| 同一次运行中记住前文 | 有 |
| 关闭程序后继续记住 | 没有 |
| `/resume` 恢复旧对话 | 没有 |
| 从大量历史中选择相关记忆 | 没有 |
| 自动提取姓名、偏好等长期信息 | 没有 |
| 历史过长后自动压缩 | 没有 |

因此有两种说法都成立：

- 从用户体验看：**V0.2 有短期记忆。**
- 从实现机制看：**V0.2 只有消息历史，还没有独立的 Memory 系统。**

等以后把 `messages` 保存为文件或数据库，并能重新加载，就是 **Session 持久化**；如果还能提取重要事实、跨会话保存并按需检索，才更接近专门的 **Memory 系统**。

验收结果：

- 有 Tool Call 时执行工具并继续循环。

| 无 Sandbox | `session-007.jsonl` | 让 Agent 通过 `bash` 删除虚构测试文件 | 删除成功，`os.path.exists=False` | `Test-Path=False` |
| 加入 Sandbox | `session-008.jsonl` | 使用完全相同的指令再次删除 | `Error: Sandbox blocked tool: bash` | `Test-Path=True` |
| 白名单验证 | `session-008.jsonl` | 调用 `word_count` 统计 `sandbox allows safe tools` | `Word count: 4` | 安全工具正常运行 |

解决方法：

```text
Tool Call
  → sandbox.check(tool_name)
  → 白名单内：执行工具
  → 白名单外：返回 PermissionError
```

验收结果：

- 无 Sandbox 时，Agent 可以通过 `bash` 删除测试文件。
- 加入 Sandbox 后，相同的 `bash` Tool Call 返回 `Error: Sandbox blocked tool: bash`。
- 删除命令没有执行，`Test-Path` 返回 `True`。
- 白名单中的 `word_count` 正常执行，返回 `Word count: 4`。
- 当前实现属于工具级 Sandbox，不包含操作系统级或路径级隔离。

核心成果：

```text
Tool Call
  → Sandbox 检查
  → 允许：执行工具
  → 拒绝：返回错误，不产生副作用
```

## 2026-10-21

### V0.14 — Durable Run

**状态：测试通过**

`micro-pi` 已支持使用 Checkpoint 保存 Parent Run 的执行位置，并在进程崩溃后恢复原 Tool Call。Session 继续保存消息历史，Checkpoint 单独保存运行状态和待执行工具。

```text
Session：保存已经发生的消息
Checkpoint：保存任务停在哪里
Resume：重新启动后从 Checkpoint 继续
```

| 阶段 | 代码范围 | 作用 |
|---|---:|---|
| 引入 Durable Run | `main.py` 17–18 行 | 导入 Checkpoint 的保存与读取函数 |
| 定义运行文件 | `main.py` 55–64 行 | 配置 Checkpoint 和一次性崩溃标记路径 |
| 保存 Checkpoint | `durable.py` 5–16 行 | 将状态和待执行 Tool Call 覆盖写入 JSON |
| 读取 Checkpoint | `durable.py` 19–23 行 | 启动时读取上一次执行位置 |
| 判断是否恢复 | `main.py` 630–642 行 | 识别 `RUNNING`、`WAITING_TOOL` 并取出待执行工具 |
| 恢复或接收任务 | `main.py` 660–692 行 | 未完成 Run 跳过输入，新任务正常进入外层循环 |
| 执行与状态流转 | `main.py` 695–790 行 | 在模型调用、工具执行和最终回答之间更新状态 |
| 模拟进程崩溃 | `main.py` 750–756 行 | 第一次 Tool Call 后、Tool Result 前主动中断 |

对比实验：

```text
第一次运行
  → user 写入 Session
  → Checkpoint = RUNNING
  → 模型生成 word_count Tool Call
  → assistant(tool_call) 写入 Session
  → Checkpoint = WAITING_TOOL
  → 工具执行前模拟崩溃

第二次启动
  → History: 2 messages
  → Run resumed: WAITING_TOOL
  → 跳过 input 和模型调用
  → 执行原 word_count Tool Call
  → Tool Result: Word count: 4
  → Checkpoint = RUNNING
  → 模型生成最终回答
  → Checkpoint = SUCCEEDED
```

恢复时的双层循环：

```text
外层循环第一次
  → resume_run = True
  → 跳过 input
  → 取出 Checkpoint 中的原 Tool Call

内层循环第一次
  → tool_calls 不是 None
  → 跳过模型调用
  → 执行工具并保存 Tool Result
  → Checkpoint = RUNNING
  → tool_calls = None

内层循环第二次
  → tool_calls is None
  → 调用模型生成最终回答
  → Checkpoint = SUCCEEDED
  → 退出内层循环

外层循环第二次
  → resume_run = False
  → 等待新的用户输入
```

最终文件：

| 文件 | 最终内容 | 说明 |
|---|---|---|
| `sessions/session-012-parent.jsonl` | 4 条消息 | 完整保存崩溃前后的消息链 |
| `runs/run-012.json` | `SUCCEEDED`、空 `tool_calls` | 当前 Run 已完成，无需再次恢复 |

最终消息链：

```text
user
  → assistant(tool_call A)
  → 程序崩溃并重新启动
  → tool(result for A)
  → assistant(final answer)
```

#### 流程说明

这次是一次真正的 Resume：第二次启动没有重新输入任务，也没有重新调用模型生成新的 Tool Call，而是执行了第一次遗留的 Tool Call。

##### 一、第一次运行：产生 Checkpoint 后崩溃

**1. 接收用户输入**

外层循环正常读取：

```text
请只调用 word_count 工具统计：durable run needs recovery
```

Session 写入第 1 条：

```json
{
  "role": "user",
  "content": "请只调用 word_count 工具统计：durable run needs recovery"
}
```

Checkpoint 状态先变为：

```text
RUNNING
```

**2. 模型生成 Tool Call**

此时：

```python
tool_calls is None
```

所以内层循环调用模型。模型决定调用 `word_count`，Session 写入第 2 条：

```json
{
  "role": "assistant",
  "tool_calls": [
    {
      "id": "chatcmpl-tool-b12e36c287c19383",
      "function": {
        "name": "word_count",
        "arguments": "{\"text\": \"durable run needs recovery\"}"
      }
    }
  ]
}
```

Checkpoint 随即保存为：

```text
status = WAITING_TOOL
tool_calls = word_count Tool Call
```

**3. 模拟崩溃**

Runtime 显示 Tool Call，但在真正执行工具之前抛出异常：

```text
Tool Call 已保存
  → Checkpoint 已保存
  → Tool 尚未执行
  → 程序崩溃
```

此时磁盘状态：

```text
Session：2 条消息
Checkpoint：WAITING_TOOL
```

##### 二、第二次启动：自动恢复

终端显示：

```text
History: 2 messages
Run resumed: WAITING_TOOL
```

这两行分别说明：

```text
History: 2 messages
  → Session 恢复了 user 和 assistant(tool_call)

Run resumed: WAITING_TOOL
  → Checkpoint 告诉 Runtime：存在待执行工具
```

代码得到：

```python
resume_run = True
pending_tool_calls = [word_count Tool Call]
```

##### 三、外层循环跳过用户输入

因为：

```python
if resume_run:
```

成立，所以执行：

```python
tool_calls = pending_tool_calls
resume_run = False
```

此时：

```text
tool_calls = [word_count Tool Call]
```

程序没有执行 `input("> ")`，所以不需要重新输入任务，也没有在 Session 中产生重复的 user 消息。

##### 四、内层循环跳过模型调用

此时 `tool_calls` 已经包含原来的 `word_count`：

```python
if tool_calls is None:
```

条件为 `False`，所以不会重新调用模型，而是直接进入：

```python
for tool_call in tool_calls:
```

执行原来的工具请求。

##### 五、执行原 Tool Call

因为崩溃标记已经存在，这次不会再次模拟崩溃：

```python
if not crash_flag_path.exists():
```

条件为 `False`。

随后执行：

```python
tool_result = tool["execute"](**tool_arguments)
```

得到：

```text
Word count: 4
```

Session 写入第 3 条：

```json
{
  "role": "tool",
  "tool_call_id": "chatcmpl-tool-b12e36c287c19383",
  "content": "Word count: 4"
}
```

最关键的验证是 ID 一致：

```text
原 Tool Call ID = chatcmpl-tool-b12e36c287c19383
Tool Result ID   = chatcmpl-tool-b12e36c287c19383
```

这证明执行的是第一次崩溃前遗留的 Tool Call，不是重新生成的调用。

工具完成后：

```python
save_checkpoint(checkpoint_path, "RUNNING")
tool_calls = None
```

含义是：

```text
工具已经完成
  → 当前没有待执行工具
  → 下一步应该调用模型
```

##### 六、模型根据 Tool Result 生成最终回答

内层循环再次开始。

这次：

```python
tool_calls is None
```

条件成立，所以调用模型。

模型看到完整上下文：

```text
用户要求统计单词
  → 模型请求 word_count
  → word_count 返回 4
```

于是返回最终答案，Session 写入第 4 条：

```json
{
  "role": "assistant",
  "content": "“durable run needs recovery” 的单词数是 **4**。"
}
```

模型没有继续请求工具，因此：

```python
if not tool_calls:
```

成立，Checkpoint 更新为：

```json
{
  "status": "SUCCEEDED",
  "tool_calls": []
}
```

##### 七、最终结果

Parent Session 最终形成完整消息链：

```text
#1 user
  → 提出任务

#2 assistant
  → 生成 word_count Tool Call
  → 第一次运行在这里崩溃

#3 tool
  → 第二次启动后恢复执行
  → 返回 Word count: 4

#4 assistant
  → 根据 Tool Result 生成最终回答
```

完整状态流：

```text
RUNNING
  → WAITING_TOOL
  → 程序崩溃
  → 重新启动
  → 恢复原 Tool Call
  → RUNNING
  → SUCCEEDED
```

这次和之前“重新输入任务”的本质区别是：

| 之前 | 现在 |
|---|---|
| 重新输入用户任务 | 没有重新输入 |
| 模型生成新的 Tool Call | 使用原来的 Tool Call |
| 出现两条 user 消息 | 只有一条 user 消息 |
| 原 Tool Call 没有结果 | 原 Tool Call 得到匹配的 Tool Result |
| 属于重新执行 | 属于断点恢复 |

`/exit` 在保存用户消息之前就被处理，因此不会写入 Session。最终 Session 正好保持四条完整消息。

验收结果：

- 第二次启动没有要求用户重新输入任务。
- Runtime 读取 `WAITING_TOOL` 后直接执行原来的 `word_count`。
- Tool Result 与崩溃前的 Tool Call 使用相同 `tool_call_id`。
- Session 中没有重复 User Message，也没有生成新的 Tool Call。
- 工具返回 `Word count: 4`，模型随后输出最终回答。
- Checkpoint 最终从 `WAITING_TOOL → RUNNING → SUCCEEDED`。
- 当前仅实现最小 Checkpoint 与 Resume，不包含自动 Retry、Heartbeat 和幂等执行保证。

Session
  + Checkpoint
  + Resume
  + Original Tool Call ID
